# Qwen3-30B-A3B accuracy tuning and focused-retrieval benchmark

**Benchmark date:** 2026-09-03
**Project:** Field Tech Copilot
**Testing priority:** Diagnostic accuracy first, response speed second

## Summary

Field Tech Copilot was tested offline with `qwen/qwen3-30b-a3b-2507`
on a Dell Latitude 5550 upgraded to 64 GB of dual-channel DDR5 memory.

This work does not fine-tune model weights. It improves the application
through:

- Curated procedure cards
- Explicit safety and diagnostic-order guardrails
- Prompt-policy tests
- Focused retrieval for clear diagnostic symptoms
- Repeatable local-model benchmarks

Qwen3-30B-A3B ran successfully on this hardware and provided substantially
better diagnostic behavior than the earlier 8B and 14B tests. Focused APIPA
retrieval reduced measured model time from 223.18 seconds to 66.25 seconds
without losing the correct DHCP diagnosis.

A seven-case application benchmark subsequently achieved the intended
knowledge citation in all seven cases, with an average end-to-end response
time of 76.90 seconds.

## Application changes

### BitLocker recovery guardrails

Added policy and test coverage for authorized BitLocker recovery scenarios,
including:

- Requiring authorized recovery-key paths
- Preventing unsupported bypass guidance
- Separating stable locked media from failing-media recovery
- Preserving customer-data safety
- Prompt-policy and deterministic guard tests

Commit:

- `0d2f6be Complete BitLocker recovery prompt guardrails`

### Windows APIPA and DHCP handling

Added a Microsoft-sourced APIPA procedure card and application rules that:

- Recognize `169.254.x.x` as failure to obtain a usable DHCP lease
- Prioritize DHCP and address-scope diagnosis before DNS
- Use `ipconfig /all` and comparison with another device as safe evidence
- Prevent premature public-IP or DNS tests while APIPA remains unresolved
- Permit DNS diagnosis after valid addressing and gateway reachability

Commit:

- `8f47902 Prioritize DHCP diagnosis for Windows APIPA cases`

### Focused knowledge routing

The original full-text retrieval returned six cards even when one card was
overwhelmingly relevant. In the APIPA benchmark, five unnecessary cards added
8,589 characters of unrelated context.

Focused routing was added for explicit:

- APIPA and DHCP symptoms
- Confirmed DNS-only failures
- BitLocker-locked media
- Mechanically unstable drives
- Printer queue and offline cases
- Blank-display cases
- Battery-drain and unplugged-shutdown cases

Ambiguous queries continue using the existing full-text retrieval behavior.

Commit:

- `2f2e9cc Route clear symptoms to focused knowledge cards`

## Accuracy observations

### APIPA and DHCP

The model correctly treated `169.254` addressing as a DHCP problem, avoided
premature DNS troubleshooting, and selected another device on the same
network as the safest discriminating test.

### DNS-only failure

Given valid DHCP, a working gateway, and successful direct-IP reachability,
the model correctly selected `nslookup` against the default resolver.

### BitLocker

The model respected the locked volume and unavailable-key condition. It
selected authorized recovery-key retrieval rather than suggesting a bypass.

### Unstable drive

The model correctly recognized clicking, disconnection, and SMART warnings
as signs of possible mechanical failure. It advised no further testing or
access and recommended professional recovery.

The benchmark displayed blank `NextTest` and `Risk` fields for this case
because the harness only reads `assessment.next_test`. It should also
understand escalation and intervention responses.

### Printer queue

The formal next test was appropriate and read-only: verify printer presence
and status in Windows Settings.

The technician message also mentioned power-cycling the printer and
restarting Windows. This reveals an application consistency issue: narrative
fields can introduce actions that are not represented by the formal
`next_test`.

### Blank display

The model correctly selected a known-good external display and cable to
discriminate between an internal-panel problem and a broader video-path
failure.

### Battery shutdown

The model correctly selected the built-in Windows battery report as a safe,
read-only diagnostic.

## Known limitations and recommendations

1. Keep accuracy first. The 30B-A3B model is now fast enough for practical
   offline use on this 64 GB laptop. Reducing model size is not currently
   necessary.

2. Enforce response-field consistency. `technician_message` should not
   introduce tests, interventions, resets, or power cycles that are absent
   from the structured `next_test` or `intervention`.

3. Make the benchmark escalation-aware. A correct stop-and-escalate response
   should not appear incomplete merely because `next_test` is null.

4. Consider configurable routing. The current focused routes use explicit
   card identifiers. Before general upstream adoption, these rules may fit
   better in card metadata or a configurable routing layer rather than
   remaining hard-coded in the knowledge store.

5. Preserve generic retrieval for ambiguity. Focused routing should activate
   only for strong diagnostic signals. Ambiguous complaints should retain
   broader retrieval.

6. Add paraphrase and collision tests. Each route should be tested with
   alternate wording and nearby but distinct conditions, such as valid DHCP
   versus APIPA, a stable drive versus a clicking drive, and battery shutdown
   versus thermal shutdown.

7. Retain the current runtime settings. Context 8192, full GPU offload, Flash
   Attention, one concurrent prediction, and the present batch settings
   produced stable results. Further runtime tuning should be isolated and
   measured after accuracy coverage expands.
